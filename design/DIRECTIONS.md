## Fuentes primarias comprobadas

- [Linear, producto](https://linear.app/features) y [modelo conceptual](https://linear.app/docs/conceptual-model): referencia para organizar trabajo por entidades y reducir fricción. Las páginas públicas no acreditan todos los estados de su aplicación privada.
- [IBM Carbon, tabla de datos](https://www.carbondesignsystem.com/building-blocks/core/components/data-table/guidelines): toolbar, jerarquía, densidades y revelado progresivo. Se estudian patrones, no se propone instalar Carbon.
- [Grafana, diseño de dashboards](https://grafana.com/docs/grafana/latest/visualizations/dashboards/build-dashboards/best-practices/): jerarquía por pregunta, comparabilidad y reducción de carga cognitiva. Es referencia de criterio, no una propuesta de incorporar Grafana ni sus paneles al SaaS.

Se observaron además en Chromium [Swisscom SDX](https://sdx.swisscom.com/latest), como referencia de jerarquía documental y componentes, y [Vitsœ / Good design](https://www.vitsoe.com/rw/about/good-design), como referencia editorial complementaria de proporción y claridad, no como software empresarial. [Registro del navegador](evidence/reference-browser.json). Las imágenes de terceros quedan solo en runtime ignorado, no se redistribuyen. Linear respondió 200 pero la captura inicial mostró el contenido central sin terminar de renderizar: la inferencia sobre sus pantallas privadas se limita a su documentación. SBB devolvió 403 y no se usa como referencia observada. [Estado de acceso](evidence/reference-access.json). No se usan como prueba de premios ni se atribuyen comportamientos a pantallas no observadas. No se copian screenshots, CSS ni assets protegidos. “Suizo” describe la intención editorial de precisión, no un premio, certificación o residencia de infraestructura.

## Comparación completa

| Criterio | A — Registro suizo | B — Atelier de operaciones | C — Mesa de control |
|---|---|---|---|
| Filosofía | Precisión de un registro operativo: leer, detectar, actuar. La identidad surge de proporciones, alineación y datos reales | Cuidado profesional de personas y lugares; carácter editorial con ritmo cronológico, sin marketing dentro de cada módulo | Supervisión coordinada del día: tiempo, cobertura y excepción en un mismo plano |
| Referencias | Carbon para filas/toolbar; Linear para entidades y foco de tarea | Vitsœ para proporción editorial y SDX para estructura reconocible; Carbon para controles familiares. La serif es propuesta propia, no atribuida a estas fuentes | Grafana para pregunta y alertas; Carbon para detalles y columna de datos |
| Tipografía | Familia actual o fallback sistema; 14px cuerpo, 12px metadatos, 24–32px título, cifras tabulares | Mismo sans en controles/datos; alternativa Georgia local en título/fecha y horas, a validar. Nunca serif pequeña en tabla | Sans actual, 14px operación, números tabulares y marcas temporales alineadas; sin fuente externa |
| Composición | Cabecera baja, métricas sin cuatro tarjetas, registro central y margen de revisión. Superficie cálida con líneas escasas | Lateral compacto con nombre completo, fecha editorial, lista cronológica y dossier de decisiones. Espacios jerárquicos, no cuadrícula uniforme | Barra superior verde, resumen fino, lienzo temporal y cola de excepciones; el eje del tiempo es el elemento propio |
| Navegación | Agrupación horizontal de cinco módulos existentes, contexto de escenario visible; búsqueda/acciones permanecen en módulo | Lateral textual estrecho justificado por exploración entre módulos; menos bloque promocional | Navegación superior, contexto de escenario y acceso a filtros del tablero; sin rail de iconos inexplicados |
| Datos/tablas | Filas alineadas, números a la derecha, toolbar fija al listado, selección/sort solo si existen funcionalmente | Lista jerárquica por jornada; directorios futuros siguen filas con controles homogéneos. Evitar tarjetas para todo | Carriles de servicios con intervalos y etiqueta textual de riesgo; tabla accesible equivalente como requisito futuro, no motor de planificación nuevo |
| Movimiento | Feedback 120–160ms; sin entradas secuenciales ni cifras animadas | Apertura de detalle discreta 160–200ms; reduced motion conserva foco/estado sin desplazamiento | Cambios de selección 120ms; no movimiento constante del tablero ni autoscroll; lo crítico no depende de animación |
| Móvil | Resumen de riesgo antes del registro; filas apiladas con hora visible y target amplio. El estudio ilustra composición, requiere ajuste de prioridad antes del piloto | Cabecera compacta, fecha secundaria, registro único; voz editorial debe reducirse para no desplazar el trabajo | Eje temporal se convierte en agenda textual con horario/cobertura completos; no forzar timeline diminuta ni scroll 2D |
| Ventajas | Mayor legibilidad y densidad útil; escala a listas de cientos de filas; bajo coste de bundle | Más personalidad sin inventar colores; expresa calidad de servicio y personas; conserva orientación de sidebar | Más original y propio del dominio; ayuda a comparar intervalos/cobertura y orientar al planner |
| Limitaciones | Menos expresiva en una captura aislada; top-nav necesitará agrupación cuando aumenten módulos | Puede sacrificar densidad o coherencia si la serif se extiende demasiado; requiere validar títulos largos y lenguas | Con datos masivos exige virtualización o paginación razonada; mayor trabajo de accesibilidad; no todos los módulos justifican timeline |
| Encaje CleanOps | Muy alto para administración, CRM y resumen operativo. Recomendada como base inicial | Alto para dirección y coordinación de equipos; alternativa si el propietario aprueba la evolución tipográfica | Alto para coordinación y futuro planning; menor para formularios administrativos |
| Coste relativo | Bajo–medio. Contenido dashboard estimado 1–3 días tras aprobación; shell no incluido | Medio. 2–4 días incluyendo revisión tipográfica; shell separado | Alto. 3–5+ días para equivalente semántico, responsive y prueba de escalas; no incluir nuevo backend |
| Riesgos de accesibilidad/rendimiento | Tablas densas: vigilar target, zoom, foco y contraste. No dependencias nuevas; coste JS esperado bajo, aún sin benchmark | Contraste/fuente/line-height y orden de lectura; fuentes locales no añaden descarga; no afirmar métrica de velocidad | No depender de color ni posición temporal; ofrecer texto equivalente, nombres y teclado. Evitar librerías de gráficos por defecto; rendimiento con volumen por medir |

## Recomendación concreta

Escoger **A — Registro suizo** para el contenido de `/demo`. Mejora legibilidad, jerarquía y densidad con menor riesgo y conserva las capacidades existentes. Adoptar después de aprobación una pequeña pieza distintiva: hora + cobertura + advertencia textual junto a cada servicio. Esa gramática procede de la operación de limpieza y evita un dashboard intercambiable.

Los tres estudios muestran alternativas de shell para hacer visible la dirección, pero cambiar navegación global queda fuera del primer piloto. Ninguna opción incorpora nuevas acciones operativas, valida cumplimiento laboral, modifica permisos o activa autenticación.

Antes de programar: el propietario debe aprobar A, B o C y la pantalla `/demo`. El sistema de diseño se concretará con esa decisión; los estudios son `DESIGN_ONLY`, no una dirección ya aceptada.
