# Home server Switzerland → compatible VPS/dedicated host

Owner decision: eventual infrastructure is an expandable home server physically in
Switzerland, with portability to commercial VPS/dedicated servers. Purchasing the
final hardware is NOT a prerequisite for synthetic technical tests. Owner remains
only a candidate principal custodian; secondary and actual quorum are unapproved.

Current isolated tests use synthetic material on a fresh Actions runner. Runner
geography is not asserted Swiss. They do not establish real residence, availability,
dual-person custody, productive key management or full B1 recovery acceptance.

## Later installation procedure — not executed/authorized here

1. Identify actual Swiss home host and isolated guest/service account, operator,
   custodians and private resource inventory; confirm residence privately (physical
   site attestation, asset/backup/media inventory, support/processing boundaries).
   Publish only a reference/hash to that inventory, never home address or secret.
2. Approve the exact non-production resources/config/policies/quorum and drill scope.
   Dedicated encrypted guest/storage, restricted OS administration, swap/core-dump
   policy, clock synchronization, tested disk capacity, power-loss shutdown/UPS and
   recoverable boot/storage custody must be reviewed for the actual home threat model.
   A backup in the same house/power/fire domain is not independent recovery storage.
3. Use maintained compatible Linux/amd64 or arm64. Choose the matching pinned release
   asset; verify SHA256 and independent signer trust/advisories before installation.
   Record build/config hashes and service ownership. Do not install from `latest`.
4. Render the existing JSON templates with real approved PRIVATE addresses/DNS and
   exact single-tenant policies. Install outside application/production identities.
   Expose8200 only on the approved private route with verified TLS/mTLS;8201 only to
   approved peers if present. No residential router forwarding, public bind, UPnP
   opening, shared production CA/keys or cloud dashboard exposure is implicit.
5. Establish private operator/workload access using the separately approved mechanism;
   dynamic public home IP/ISP availability does not justify public OpenBao exposure.
   Initialize actual custody only after the named people and quorum are confirmed;
   use CUSTODY_AND_RECOVERY.md, no CI/plaintext initialization transcript.
6. Install exact reviewed mount/policy/role definitions; pass native configuration,
   TLS, least-privilege, tenant/purpose, audit, rotation and restore tests on the real
   isolated resources. Bind the actual B1 custody adapter through approved existing
   capabilities; missing resolver/HMAC-version migration remains real work, not a
   capability supplied by policy files. No new SQL/ACL is installed implicitly.
7. Schedule encrypted independent Swiss backups with measured recovery point/lag and
   retention, run complete authorized B1/PG/files/config/key recovery, measure existing
   RPO≤15min/RTO≤4h targets. Synthetic OpenBao-only timings do not establish those.
8. Obtain independent review and execute the existing10-step manual PO dossier. Retain
   real observations/receipts and formal decision before PR006/PR007/B1 closure.

## Portable migration (separate future authorization)

Portability is a tested recovery procedure, not moving a live data directory or
sharing disks. Keep versioned configs, exact release/architecture digests, paths,
TLS/DNS/trust, tenant/key-version manifests and encrypted Raft/PG/config backups
outside the hardware failure domain. A real VPS must have documented Swiss compute,
backup, support and recovery locations; its marketing region alone is insufficient.

Approve NEW target → verify version/trust/private isolation → snapshot and coherent
security-state checkpoint → encrypted transfer within the approved boundary → restore
(original quorum; separately authorized snapshot-force only for a fresh incompatible
seal) → reissue/revoke workload credentials and reconcile monotonic B1 state → run
real checks → explicit cutover approval. Do not run competing issuers against stale
security state, copy productive keys into CI or decommission the last recoverable
source before validation. No migration, cutover or production activation occurred.

This does not introduce another product module or a new SLA; it prepares the existing
Swiss custody/recovery and PR006 obligations for the owner's selected hardware model.
