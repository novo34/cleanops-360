## Capacidad acreditada y alternativa mínima

El repositorio acredita Next.js 16.4.3, `next start`, router HTTPS de Traefik y red privada. No acredita versión/configuración efectiva de Traefik, saneamiento del origen ni un emisor autenticado. Los campos nulos del RESOURCE_RECORD no son observaciones del VPS. NextRequest no expone aquí un TLSSocket autenticado; Proxy/ALS no convierten cabeceras en identidad.

La documentación oficial de [ForwardAuth](https://doc.traefik.io/traefik/reference/routing-configuration/http/middlewares/forwardauth/) ofrece `forwardBody`, `maxBodySize`, `authRequestHeaders`, `authResponseHeaders` (reemplaza cabeceras conflictivas), `tls.ca/cert/key`. Debe verificarse su disponibilidad exacta en la versión instalada; la documentación actual de confianza de forwarded headers incluye diferencias/deprecaciones entre versiones. [Headers](https://doc.traefik.io/traefik/reference/routing-configuration/http/middlewares/headers/) añade/reemplaza valores, no firma aserciones. [Dominios Dokploy](https://docs.dokploy.com/docs/core/domains) configura routing, no acredita metadatos por sí mismo.

Alternativa propuesta: middleware ForwardAuth nativo hacia un listener HTTPS privado dentro del proceso/contenedor web existente; handler Node sin servicio, plugin, CA ni base de datos adicionales. El adaptador existe y se prueba con TLS real local. NO existe aún el bootstrap/listener en el arranque real `next start`: falta ese hook y su revisión. No se añade en este encargo, no se cambia instrumentation ni sus pins. No hay evidencia para declarar autorizado el certificado del Agent como identidad del proxy: NO se copia ni reutiliza.

ForwardAuth debe tener acceso a las mismas cabeceras vinculadas y cuerpo que llegarán a Next; el adaptador fija Host al host original autenticado. Solo acepta XFF de un salto, método/protocolo/host/URI únicos y exactos desde un socket TLS autorizado con fingerprint SHA-256 fijado. TLS identifica al proxy; la IP solo queda acreditada si su configuración impide que el navegador imponga esos campos. Una cadena XFF se rechaza: si existe otro balanceador, falta acreditar y adaptar explícitamente ese límite, no se elige arbitrariamente un elemento.

No se entrega YAML operativo con nombres/IDs inventados. Requisitos concretos del futuro cambio del router: saneamiento de todas las X-Forwarded usadas, trustedIPs reales (nunca trust universal), `forwardBody` y límite finito compatibles con la versión instalada, copia exclusiva de la cabecera de aserción, reemplazo de cualquier aserción del cliente, sin caché/reintentos que reutilicen aserciones, sin transformaciones posteriores del cuerpo/cabeceras vinculadas, sin ruta pública al emisor. La web seguirá verificando firma aunque se omita o eluda el middleware.

## Slice implementado y límites

QG-0: se reutilizan canonical/valid, límites B1, validación de etiquetas, lector privado y contexto ALS; no se modifica runtime, loader, SQL ni contratos actuales. Dos responsabilidades nuevas justifican módulos separados: política de correo compartida y protocolo de ingreso. Ningún módulo nuevo se importa desde el arranque o rutas activas.

- `email-normalization.ts`: política PROPUESTA `b1-ascii-domain-lower-v1`; conserva local-part exactamente, baja solo dominio ASCII, rechaza whitespace/Unicode en lugar de adivinar equivalencias. No describe ninguna política histórica. Reporte determinista de snapshot completo con IDs estables y `emailNormalized` exactos: cuenta inválidos/cambios/colisiones; cualquiera bloquea. No altera identidades ni produce SQL. Cero filas exige aprobación explícita. El mismo callback aprobado debe pasarse al provisionador y autenticación; no se conecta unilateralmente a ninguno.
- `check-b1-email-compatibility.mjs`: análisis offline de JSON privado fuera del checkout, permisos 0400/0600, uid/gid exactos, lector sin symlinks, máximo 64 KiB; salida solo conteos/hashes. Para snapshots mayores falta una extensión revisada del lector/análisis, no truncar ni muestrear. Uso local autorizado: `node --experimental-strip-types scripts/check-b1-email-compatibility.mjs ABSOLUTE_SNAPSHOT UID GID 0600`. No extrae ni consulta PostgreSQL. El propietario debe asegurar totalidad/frescura y congelar el provisionamiento entre snapshot y adopción; un hash no prueba exhaustividad.
- `ingress-assertion.ts`: Ed25519 con dominios distintos para credencial/aserción; formato canónico, campos exactos, issuer/audience fijos, timestamps en milisegundos, nonce aleatorio de 32 bytes. Vincula método, origen HTTPS configurado, path/query, cuerpo SHA-256 y Host, Authorization, Cookie, Origin, Content-Type/Encoding, X-CSRF-Token, Idempotency-Key y Sec-Fetch-Site. La cabecera de aserción se excluye de su propio binding. Lectura acotada en tamaño/tiempo sin consumir el body del handler. Firma o metadatos inválidos => dependencia no disponible antes de efectos.
- Red: IP del hop acreditado convertida en pseudónimo HMAC de 32 bytes; dispositivo: ID aleatorio de credencial firmada convertido por HMAC con separación de dominio. Sin IP, ID de navegador, UA o etiquetas del cliente como identidad. Labels solo del enrolamiento aprobado, firmadas y validadas.
- La credencial es un bearer firmado de perfil lógico enrolado: verificable, pero copiable si se roba. NO es hardware, prueba de posesión, MFA ni sustituto del login/TOTP. La función de emisión solo la invoca código de enrolamiento confiable; deliberadamente no existe endpoint público de autoemisión. Sin credencial no hay contexto, también en primer login. El canal de entrega debe exigir HTTPS, Secure, HttpOnly, Path=/, sin Domain y política SameSite aprobada. Revocación por dispositivo y recuperación/enrolamiento no están implementados: deben resolverse antes de aceptar esa semántica, o cambiar el contrato a una credencial con prueba de posesión si el propietario exige esa propiedad.
- TTL de contexto explícito <=30 s, sin tolerancia de reloj; credencial/TTL/body/timeout/audience/emisor/capacidad son configuración explícita, no valores históricos ni operativos elegidos. Se rechazan contextos que sobrevivan a su credencial. No hay renovación implícita.
- Antirreplay: claim sin await después de validar binding, capacidad finita, sin expulsión de nonces vivos; caché llena falla cerrada. Instancia única por proceso/consumidor. Al reiniciar rechaza `iat <= epoch` (también el milisegundo exacto del arranque); retroceso de reloj falla cerrado. Requiere reloj coherente no decreciente y un único proceso consumidor. NO cubre múltiples workers/réplicas/rolling overlap ni rollback del reloj tras reinicio: en esos escenarios hace falta un almacén atómico compartido o un esquema de épocas coordinado previamente aprobado. No se presume Redis disponible ni se crea uno.
- `ingress-forward-auth.ts`: autentica TLSSocket y fingerprint exacto ANTES de interpretar cabeceras/cuerpo; handler sin listener ni endpoint instalado. 403 sin detalles ante fallos.
- `integration-candidate.ts`: factory y renderer del módulo privado con exactamente `normalizeEmail` y `resolveRequestContext`. Renderer incorpora recibo y configuración pública en los bytes del módulo, sin import de configuración privada mutable; exige Date.now y URL file estática del helper. Se carga realmente como data URL en tests, igual que exige el loader existente. El helper y dependencias deben estar fijados en la imagen inmutable revisada; el hash del wrapper por sí solo NO cubre imports transitivos. No se genera un artefacto instalable con un recibo de aprobación inventado.

El emisor exige clave de firma Ed25519 y clave HMAC dedicada 32 bytes; el verificador solo recibe clave pública. No se generan claves de producción. Inventariar primero material ya existente apto y autorizado: no reutilizar automáticamente cinco claves de custodia, dummy PHC, corpus, certificado Agent ni clave TLS para firmar. Si no existe material de este propósito, falta autorización para ese material mínimo; no son duplicados creados aquí. Los tests generan exclusivamente claves/certificados efímeros y los eliminan.
