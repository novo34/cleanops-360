## Idempotencia y concurrencia

Idempotency-Key obligatorio16..128 ASCII para mutaciones salvo login y verifyMfa. Scope activo=tenant+user+operation+key; scope ceremonia=digest del binding preauth+operation+key. Hash canónico de request SHA256 calculado por servicio; nunca body secreto persistido. Misma clave/distinto hash→409 IDEMPOTENCY_MISMATCH. Una transacción reserva, bloquea, ejecuta, audita y completa; no commit de reserva separada. Concurrencia espera fila/lock y devuelve resultado confirmado seguro, no segundo efecto. TTL propuesto24h; clave caducada da409 y nuevo intento usa nueva clave, sin reutilizar autorización antigua.

OTP consume exactamente una vez; verifyMfa no es reejecutable con éxito por repetir código. Post-verificación el cliente puede leer /auth/me con cookie confirmada; si perdió respuesta y cookie, reinicia ceremonia segura. Para QR/códigos, idempotencia guarda solo marcador one_time_result, no plaintext; repetir éxito con binding todavía válido da409 RESULT_NOT_REPLAYABLE; si la ceremonia ya fue consumida o expiró, devuelve401 sin reentregar secretos y exige nueva ceremonia para reemplazar el lote/enrollment. El middleware no vuelve a mostrar secretos. En logout/revocación de actual se completa el marcador en la misma transacción vinculada antes/dentro del commit aunque el token deje de ser válido; ese helper no permite una operación de negocio nueva con token revocado. complete_ceremony se invoca antes de consumir preauth en la misma transacción: confirmar/después emitir sesión es una única unidad, sin commit entre pasos.

Las funciones SQL son primitivas internas; la capa de servicio agrupa reservas/efectos/auditoría/completion por conexión y transacción. No se invocan por el navegador ni se exponen como API RPC. Firma/marcador no reemplaza autorización. Operaciones sin body rechazan body no vacío; DELETE propio se refiere solo a session_id. Bulk propio body Reason no acepta user_id/tenant_id/selectores, preserva current; administración ajena no forma parte de B1.
